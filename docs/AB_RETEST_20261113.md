## G3 FAIL 归因（已逐 case 定位）

P95 比值 ×3.12 的构成（原始数据见 decision.db + observations.jsonl）：

1. **浏览器恢复 6 次**（`LOW_CONTENT_DENSITY→BROWSER` 4 次 + `CHALLENGE→BROWSER` 1 次
   + `example.org` 的 AMBIGUOUS 分支）：每次走本机 playwright 冷/热启动，
   单次 3.0–6.7s。这是**恢复机制的正常工作**（且全部 browser_success），
   但它进入 P95 分位后把 pipeline 的尾延迟拉高。
   baseline 臂没有恢复机制，天然没有这部分。
2. **决策记录开销 ~0.3s/次**：`decision_store.record_event` 每次提交 sqlite
   含 WAL fsync，60 次累计 ~18s。属可观测性代价，可优化（批量写/异步落盘）。
3. **恢复分类 + quality 采样 ~0.2–0.4s/次**：纯 Python 开销，随版本累积
   （v2.6–v2.8 加了不少 classification 分支）。

结论：**G3 FAIL 是"恢复机制工作的代价"而非"抓取变慢"**——median 层面
pipeline 1429ms vs baseline 449ms（×3.2，其中 ~0.5s 是决策记录，~0.4s 是
分类，网络本体两侧一致）。但 P95 阈值 ×1.3 对带恢复臂的设计过于严格：
恢复臂的 P95 天然由"第 95 分位恰好触发恢复"决定。

## 环境发现（本次复测的副产品，值得记档）

1. **httpx 0.28.x 对 `NO_PROXY` 中的 `[::1]` 解析崩溃**（`InvalidURL: Invalid
   port ':1]'`），表现为**静默空结果**（status 0、无 error、content 空）。
   本机 AGENTS.md 5.9 标准代理配置恰好含 `[::1]`，触发此 bug。
   已用进程内覆写 `NO_PROXY=127.0.0.1,localhost,::1` 绕过（wrapper：
   `.webscout-eval/ab_eval_safe_env.py`）。
   **上游值得加一条防御**：启动时校验 NO_PROXY 可解析，不可解析项打警告
   ——这与 v2.8.0 的"空结果必须解释为什么"原则一致，目前 httpx 在
   provider 层把这个错误吞成了空串。
2. 首轮复测（`ab-retest-20261113`）就跑在这个 bug 下，60/60 双臂全 0 字符
   还全 PASS——**G1/G2 的"双臂同坏"盲区**再次验证了 GOAL_REVIEW 缺陷 1
   的判断：gate 只比相对差，环境整体坏掉时 gate 依然绿灯。报告 advisory
   里的提示（"no usable content ≠ quality acceptable"）是对的，但值得
   升级为硬约束（双臂 usable 均为 0 时 gate 应直接 BLOCKED）。

## 结论与建议

1. **G1/G2 验收通过**：Phase 4（content sufficiency）的 A/B 复测要求就此
   闭合——可用率不再劣于裸基线，−7.3pp 未复现。执行顺序第 3 步标记完成。
2. **G3 判据本身需要修订**：×1.3 阈值适用于"同构臂"，对带恢复臂应改为
   分位分层验收（median ×≤2.0 且恢复触发率受控且恢复成功率 ≥80%），
   否则每次浏览器恢复正常工作都会误报 FAIL。
3. **可观测性开销值得单独立项**：0.3s/请求的 sqlite fsync 在端到端延迟里
   占比过高，建议 batch + WAL + 后台 flush。
4. **G4（search）**：本次未覆盖，留作下一个动作。
5. **httpx NO_PROXY 防御**：建议作为 v2.8.1 的一个 fix（启动校验 +
   provider 层把 status 0 + 空 content + 无 error 的组合视为配置错误而非
   成功）。
